2. 定制版 CAD 文件解析器与清理工具的底层 Bug
在 src/app/toolbox/ 的定制工具中，有 4 个涉及真实文件处理的工具存在严重的底层逻辑错误：
* ctb-plot-style-pen-visualizer（上传 .ctb 文件实际是用字节取模伪造数据）：
   * 位置：src/app/toolbox/ctb-plot-style-pen-visualizer/calculator-client.tsx 第 207–223 行。
   * 问题：真实的 AutoCAD .ctb 文件是 PIAFILEVERSION_2.0,CTBVER1,compress\r\npmzlibcodec 文本头加上 zlib (deflate) 压缩流。当前代码发现二进制文件不是明文后，在 else 分支里写了 const hash = (uint8[0x200 + (i * 2) % uint8.length] || 0) % 8，直接拿文件字节对 8 取余数来随机编造 0.09 ~ 0.50 mm 的线宽并全部设为黑色，然后弹窗欺骗用户“成功导入 255 种 ACI 打印样式”。
   * 修复方案：定位文件头中 pmzlibcodec 换行符之后的字节偏移量，直接调用浏览器原生 new DecompressionStream('deflate') 解压出真实的 CTB 字典明文，再解析每种颜色的真实 lineweight、color 和 screening。
* drawing-lag-performance-cleaner（在线清理 DXF 会损坏文件导致 AutoCAD 报错拒开）：
   * 位置：src/app/toolbox/drawing-lag-performance-cleaner/calculator-client.tsx 第 55–66 行。
   * 问题：代码用正则 /ACAD_PSEUDO_DXF|AECTOOLS_.*|AEC_.*|.../gi 将 DXF 中所有匹配的注册应用名全部替换成同一个常量字符串 'ACAD_CLN_REG'。在 DXF 的 APPID 符号表中，表项名称必须唯一；一旦原图中有 2 个以上 AEC_* 或 ADSK_* 应用，替换后就会产生重名表项，AutoCAD 打开导出的 _purged.dxf 时会直接报错 Duplicate record name "ACAD_CLN_REG" in APPID table — drawing discarded。而且仅仅替换名字并不会减小文件体积。
   * 修复方案：若做重命名脱敏，必须在替换回调中附带唯一递增序号（如 let idx = 0; cleanedText.replace(regappKeywords, () => 'ACAD_CLN_' + (++idx))）；若做瘦身清理，需按 DXF 组码状态机真正移除未被引用的 APPID 与 DICTIONARY 块。
* stl-mesh-checker（二进制 STL 误判为 ASCII 导致解析失败）：
   * 位置：src/app/toolbox/stl-mesh-checker/calculator-client.tsx 第 35–36 行。
   * 问题：代码仅通过前 5 个字节是否为 'solid'（headerStr.toLowerCase().startsWith('solid')）来判断是否为 ASCII STL。实际上 SolidWorks、Rhino、Blender 等软件导出的大量 Binary STL 其 80 字节文件头同样以 "solid" 开头，导致这些二进制文件走入 ASCII 正则分支，匹配出 0 个三角形并直接报错 "No triangles found in STL file"。
   * 修复方案：优先读取第 80–84 字节的三角形数量 triCount = view.getUint32(80, true)，只要满足 bytes.length >= 84 && bytes.length === 84 + triCount * 50，即 100% 走 Binary STL 解析分支。
* steel-grade-selector（国标牌号过时且大小写敏感）：
   * 位置：src/app/toolbox/steel-grade-selector/calculator-client.tsx 第 17 行。
   * 问题：仅支持手敲大写 'Q235'、'Q345'、'Q390'、'Q420'、'A36'、'A572'。现行国标 GB/T 1591-2018 早已用 Q355 替代 Q345，若用户输入 'Q355' 或小写 'q345'，代码 props[grade] || {Sy:235, Su:375, el:26} 会静默回退成 Q235 的屈服强度（235 MPa），极易造成错误。应改为 <select> 下拉框并加入 Q355、S235JR、S355JR。
3. 对比页（/compare 与 /compare/[pair]）的严重逻辑与内容穿帮
* /compare 自选对比表把所有免费/开源软件的价格显示为 $TBA：
   * 位置：src/app/compare/compare-client.tsx 第 285 行：{row.type === 'price' && <span>${(val as number) || 'TBA'}</span>}。
   * 问题：当用户将 FreeCAD、Blender、KiCad、LibreCAD、OpenSCAD 等免费软件加入对比表时，它们的 starting_price 是数字 0。在 JS 中 0 || 'TBA' 为 'TBA'，再拼上前方的 $，导致所有免费/开源软件的起始价格全部显示为 $TBA。
   * 修复方案：当 tool.pricing_type === 'Free' || tool.pricing_type === 'Open Source' 时直接渲染 Free ($0)；当 val > 0 时渲染 $${val}；其余情况渲染 Custom / Quote。
* /compare/[pair] 的 CompareWidget 组件（src/components/compare-widget.tsx）存在严重的“跨领域/跨软件硬编码穿帮”：
   * 力学/流体仿真（CAE）与电子电路板（EDA）混在同一个列表里（严重违反 AGENTS.md 物理熔断红线）：在 compare-widget.tsx 的 case 'simulation'（第 200–254 行）中，第 1、2 项指标是 CFD/多物理场（Fluent vs COMSOL），第 3、4 项指标竟硬编码成了 PCB 原理图同步（Schematic & PCB Sync Integrity） 和 PCB 布线间距检查（Design Rule Check (DRC) Engine）。导致用户访问 /compare/ansys-fluent-vs-simscale 或 /compare/abaqus-vs-ansys-mechanical 时，页面下半部分在对比 Ansys 的“PCB 电路板原理图同步”并在结论里点评 Altium Designer vs KiCad；反之访问 /compare/altium-designer-vs-kicad 时，上半部分却在评估 KiCad 的“千核超算集群 CFD 流体求解器”并点评 Fluent vs COMSOL！
   * 所有类别的指标结论（metric.comparison）全部写死了固定软件名：
      * 在 mcad 类别下，哪怕用户看的是 /compare/catia-vs-siemens-nx 或 /compare/solidworks-vs-ptc-creo，展开后的 Verdict 依然硬编码写着 "Fusion 360 offers superior integrated... while Mastercam dominates..." 和 "Onshape leverages cloud parallelization..."；
      * 在 bim 类别下，哪怕看的是 /compare/tekla-structures-vs-vectorworks，Verdict 依然硬编码写着 "ArchiCAD is designed with openBIM... whereas Revit relies on..."。
   * 修复方案：将 archetype: 'simulation' 拆分为 'cae' 与 'eda' 两个独立分支；并将所有 metric.comparison 改为基于当前传入的 a.name 和 b.name 动态生成对比结论。
